# Правила написания постов

## 📝 Общие принципы

### 1. Структура поста

Каждый пост должен иметь чёткую структуру:

```
{Эмодзи категории}
**{Заголовок}**

{Введение: 1-2 предложения}

---

### 📌 Суть
{Основное содержание}

### 💻 Технические детали
{Код, примеры, версии}

### 🔍 Что это значит для вас?
{Практический контекст}

---

🔗 Источники
· {ссылка 1}
· {ссылка 2}

#теги
```

### 2. Заголовок

**Требования:**
- Максимум 80 символов
- Интригующий, но правдивый
- Содержит ключевую информацию (версию, технологию)
- Без кликбейта

**Примеры хороших заголовков:**
- ✅ `PHP 8.4.0 released: property hooks и без скобок для new`
- ✅ `Xray-core 1.8.24: улучшенная обфускация VLESS`
- ✅ `Tailwind CSS v4.0: новинки и миграция с v3`

**Примеры плохих заголовков:**
- ❌ `ШОК! Вышло обновление, которое изменит всё!`
- ❌ `Новая версия PHP` (слишком обще)
- ❌ `Разработчики выпустили очередное обновление своего фреймворка` (скучно)

### 3. Введение

**Формула:**
```
{Кто выпустил} + {что случилось} + {когда}
```

**Пример:**
> Вышел минорный, но важный релиз Xray-core. Разработчики закрыли уязвимость в логировании и улучшили маскировку трафика.

### 4. Основная часть

**Правила:**
- Используй подзаголовки для разделения блоков
- Каждый абзац — 2-4 предложения
- Списки для перечислений
- Код только в блоках ```code```

### 5. Технические детали

**Когда добавлять:**
- Есть изменения в конфигурации
- Есть примеры кода
- Нужно показать diff
- Есть конкретные версии/числа

**Формат:**
```json
{
  "version": "1.8.24",
  "feature": "vless-obfuscation"
}
```

### 6. Практический контекст

**Ответь на вопросы:**
- Нужно ли обновляться?
- Как это повлияет на проекты?
- Какие есть риски?
- Что делать читателю?

**Пример:**
> Если вы держите публичные серверы — обновление рекомендуется. Утечка памяти могла приводить к падению сервиса на маломощных VPS.

### 7. Источники

**Требования:**
- Минимум 1 источник
- Максимум 3 источника
- Только прямые ссылки
- **Обязательно оформляй как кликабельные ссылки Markdown**

**Формат:**
```
🔗 Источники

· [Название источника](URL)
· [Название источника 2](URL)
```

**Примеры:**
```
🔗 Источники

· [Официальный релиз на GitHub](https://github.com/XTLS/Xray-core/releases/tag/v1.8.24)
· [PHP.net Release Announcement](https://www.php.net/releases/8.4/)
· [Ars Technica: Apple WWDC 2026](https://arstechnica.com/apple-wwdc-2026/)
```

**❌ Неправильно (текст без ссылки):**
```
🔗 Источники

· Официальный релиз на GitHub
· PHP.net Release Announcement
```

**✅ Правильно (кликабельная ссылка):**
```
🔗 Источники

· [Официальный релиз на GitHub](https://github.com/XTLS/Xray-core/releases/tag/v1.8.24)
· [PHP.net Release Announcement](https://www.php.net/releases/8.4/)
```

### 8. Теги

**Правила:**
- 1 основной тег (категория)
- 2-4 дополнительных тега
- Без пробелов
- Нижнее подчёркивание для составных тегов

**Пример:**
```
#vpn #xray #vless #security
```

## 📐 Форматирование

### Telegram Markdown V2

| Элемент | Синтаксис |
|---------|-----------|
| **Жирный** | `*текст*` |
| _Курсив_ | `_текст_` |
| `Моноширинный` | `` `текст` `` |
| [Ссылка](url) | `[текст](url)` |
| ```код``` | ```` ```код``` ```` |
| ||Спойлер|| | `||текст||` |

### Экранирование символов

В Telegram Markdown V2 экранируй эти символы:

```
_ * [ ] ( ) ~ ` > # + - = | { } . !
```

**Пример:**
```
Вместо: PHP 8.4 > PHP 8.3
Напиши: PHP 8.4 \> PHP 8.3
```

## 🎯 Типы постов

### 1. Одиночная новость (single_post)

**Когда использовать:**
- Major/minor релиз
- Security patch
- Важный анонс

**Длина:** 150-300 слов

### 2. Дайджест (daily_digest)

**Когда использовать:**
- Нет одной доминирующей новости
- Несколько важных событий за день

**Структура:**
```
**Дайджест за {дата}**

1️⃣ {Новость 1}
{кратко}

2️⃣ {Новость 2}
{кратко}

3️⃣ {Новость 3}
{кратко}
```

**Длина:** 200-400 слов

### 3. Срочная новость (breaking_news)

**Когда использовать:**
- Критическая уязвимость
- Breaking change
- Важный инцидент

**Структура:**
```
🚨 **СРОЧНО**

{суть в одном предложении}

{детали}

{что делать}
```

**Длина:** 100-200 слов

### 4. Туториал (tutorial)

**Когда использовать:**
- How-to гайд
- Пошаговая инструкция
- Разбор технологии

**Структура:**
```
**{Название туториала}**

{введение, зачем это нужно}

---

### Шаг 1: {название}
{инструкция}

### Шаг 2: {название}
{инструкция}

---

{заключение}
```

**Длина:** 400-800 слов

### 5. Сравнение (comparison)

**Когда использовать:**
- Технология A vs Технология B
- Выбор инструмента
- Анализ альтернатив

**Структура:**
```
**{A} vs {B}: что выбрать?

{краткое описание обоих}

---

### {Технология A}
**Плюсы:**
**Минусы:**

### {Технология B}
**Плюсы:**
**Минусы:**

---

### Итог
{рекомендация}
```

## ✅ Чек-лист перед публикацией

- [ ] Заголовок ≤ 80 символов
- [ ] Есть введение (1-2 предложения)
- [ ] Основная часть структурирована
- [ ] Технические детали в блоках кода
- [ ] Есть практический контекст
- [ ] Указаны источники (1-3)
- [ ] **Источники оформлены как кликабельные ссылки [название](URL)**
- [ ] Теги соответствуют категории
- [ ] Markdown V2 корректен
- [ ] Нет экранирования ошибок
- [ ] Тема не дублируется в истории

---

**Важно:** Качество важнее количества. Лучше пропустить публикацию, чем опубликовать непроверенную информацию.
